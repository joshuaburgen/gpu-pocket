### 电脑连接手机热点的原生测试

22:31–22:36，用户将开发机从校园 Wi-Fi 切换到手机热点。电脑 WLAN 获得了与手机相同 `240e:46e:8600:3a0::/64` 前缀的全局 IPv6，存在 IPv6 默认路由。原生 Python AF_INET6 socket 能建立到清华 IPv6-only 镜像站 TCP 443 的连接，证明本轮不是只有热点 IPv4 可用。

相同原生 socket 连接服务器已监听的 SSH 99 端口超时；对服务器非临时和临时 IPv6 分别测试，均超时。热点电脑主动 ping 服务器的非临时地址也超时。电脑 Windows 防火墙的当前策略允许出站，未发现启用的出站阻止规则。该测试绕过浏览器和 HTTP 代理，已排除手机浏览器作为唯一原因。

同时在服务器抓取“服务器目标地址与该手机 /64 之间的 ICMPv6 或 TCP 99 头部”。服务器主动指定非临时 IPv6 向手机发起的 3 次 ping 全部获得回复，约 20–22 ms；指定临时 IPv6 的 3 次 ping 也全部成功。抓包记录到非临时地址发出的请求与手机回复，却未观察到热点电脑发起的 TCP 99 SYN 或 ICMPv6 Echo Request。这种方向性差异与路径上过滤外部主动流量的策略相符，但仍无法确定策略位于运营商、校园边界还是其他节点。

Quick Tunnel 在同一热点网络下通过检查：匿名 401、正确令牌 200、控制 403，真实 GPU 数量 2，采样无错误。临时诊断入口保持关闭，抓包限时结束，未改动网络或防火墙规则。下一项有价值的对照是更换热点流量 SIM 的运营商，重复同一组原生测试。

完整客户端测试记录保存在被 Git 忽略的 `.local/hotspot-tests.json`、`.local/hotspot-address-comparison.json`。服务器私有抓包目录为 `/var/tmp/gpu-pocket-hotspot-20261030-223241-1065534/`。

22:21 用户提供了关闭 VPN 后的截图，状态页不再显示先前的虚拟地址组合，而是显示 `10.225.122.143` 和一个 `240e:46e:8600:3a0::/64` 前缀的全局 IPv6。完整手机地址仅用于本次诊断，不写入此公开记录。此前 VPN 状态对浏览器测试的影响尚不能反推，本轮以关闭 VPN 后的结果为准。

服务器先后对该手机 IPv6 发起 5 次 ICMPv6 Echo，全部收到回复，往返约 19–24 ms。这证明该时段两者之间 ICMPv6 往返可达，不能据此推断校外主动 TCP 一定允许。

22:23 后的测试使用关闭 VPN 的蜂窝网络。用户报告 TCP 80 页面超时；同期服务器抓包只观察到电脑的成功对照访问，没有观察到手机蜂窝地址的 TCP 80 连接请求。随后仅改变端口和独立诊断 HTTP 实现，在 TCP 8766 测试；电脑对照成功，手机仍失败，服务器同样未观察到手机来源的连接请求。期间再次 ping 手机成功，降低了手机地址已失效的可能性。

这些结果与“校外主动 TCP 在服务器之前被过滤或未正常发出”相符，校园网边界状态防火墙是候选原因，但无法凭单端抓包确定具体设备。运营商路径以及浏览器自身的代理、加速或请求处理仍需排除。若要确认校园网侧，应使用另一个运营商或独立 TCP 客户端复测，并由网管核对同一时间、源地址、目标地址和端口的边界日志。

本轮 TCP 80 私有抓包目录为 `/var/tmp/gpu-pocket-ipv6-20261030-222318-1062153/`；8766 使用限时、仅 TCP 头的实时抓包。未修改主机防火墙或矿工配置，测试服务在诊断后关闭。

补充验证：用户确认手机在关闭 Wi-Fi/VPN 的蜂窝网络下可正常打开清华 IPv6-only 镜像站。因此当前浏览器具备访问其他 IPv6 站点的能力，不能将目标连接失败简单归结为手机不支持 IPv6。

本轮对照抓包已汇总到 [ipv6-capture-summary.json](ipv6-capture-summary.json)。电脑两个连接从首次 SYN 到首次 ACK 约为 8 ms、16 ms；未逐字确认身份的校园客户端有 5 个连接继续握手，耗时约为 70 ms、9.5 s、9.8 s、21 s、32 s，并有多次重传。不能把这一组波动笼统解释为“入站完全禁止”。

22:01:51–22:02:20，在诊断服务和抓包同时运行时再次执行外部证书机构 HTTP 验证。证书机构报告 TCP 连接超时，抓包中该时间窗口匹配到的包为 0。这把本次外部探测的问题范围缩到服务器抓包点之前或远端发起路径；它不区分运营商互联、校园边界及其他上游节点，也不直接证明手机蜂窝请求有相同原因。

服务器主动 IPv6 访问清华镜像站成功，主动访问腾讯站点也完成 TLS/HTTP 连接；主动连接 Cloudflare IPv6 目标超时。这是目标相关的连通差异，不能把单个失败扩展成“服务器所有校外 IPv6 都不通”。

本轮抓包与诊断入口已停止，Quick Tunnel 和只读 API 保持运行。下一步需要手机蜂窝运营商和来源 IPv6，才能针对同一客户端进一步核对请求及返回路由。

21:51–21:58 的同步抓包提供了更具体的证据，以下内容优先于之前按浏览器超时作出的判断：

- 电脑对照访问能完成握手和 HTTP 响应。
- 新出现的校园网客户端存在反复 SYN、服务器 SYN-ACK 重传和延迟 ACK。部分连接在约 10 秒后继续发送 HTTP 请求，服务器很快发出了响应，随后仍有重传或客户端重置。
- 用户后续修正反馈：校园 Wi-Fi 页面等待一段时间后可以打开。因此校园 Wi-Fi 应记录为可达但慢，不能记录为持续完全失败。
- 该新增客户端的完整地址只保存在私有抓包文件中，尚未由用户逐字核对是否为手机；根据测试时段和网络前缀判断与手机测试相符。
- 截至当前抓包副本，只观察到校园网前缀的客户端，未识别出蜂窝网络来源。缺少手机蜂窝 IPv6 地址及其自身 IPv6 联网验证，不能由此确定校园网边界拦截。

下一步用 IPv6-only 的清华镜像站验证手机蜂窝 IPv6 本身，再结合客户端来源地址与服务器抓包定位。主机已发出回复并不证明回复已到达手机；重传和延迟只能把排查范围缩到返回路径、丢包或客户端行为，尚不能确定具体设备。

完整 TCP 头摘要位于本机被 Git 忽略的 `.local/ipv6-capture-headers.txt`，原始记录位于远端 root 私有的 `/var/tmp/gpu-pocket-ipv6-20261030-215114-1052084/`。抓包只针对该 IPv6 的 TCP 80，不包含监控 API 8787 或令牌。诊断脚本有 15 分钟上限，退出时恢复诊断 HTTP 服务原有的停止状态。

用户确认：关闭 Wi-Fi 和 VPN 后，使用手机 4G/5G 访问标准 HTTP 80 测试入口超时或无法打开。结合证书机构从外网访问 80、443 均失败，目前只证实校园网内可达，没有可用的校外 IPv6 直连路径。限制可能位于校园网边界或外部路由，不能仅凭这些结果认定具体设备或策略。

诊断结束后关闭并禁用 gpu-pocket-ipv6.service，保留程序和配置，未启用生产 HTTPS 或续期任务。下文的 HTTP 80 测试入口记录属于测试期间状态，当前已停止。App 继续使用已验证可用的 Quick Tunnel。

后续若要继续 IPv6 方案，应由校园网管理员核实该服务器 IPv6 的校外入站策略和路由，并按许可开放 TCP 80、443。管理员确认后，可重新启用诊断服务，先验证蜂窝访问，再进行证书测试。

## 已确认的连通范围

开发机现在拥有 `2001:da8:8002:1bd1::/64` 的公网 IPv6 地址。服务器的当前非临时全局地址是：

```text
2001:da8:8002:6bd1:5d5d:9bea:1702:6bee
```

这个地址仍由路由通告动态配置，不应视为永久静态地址。另有临时和已弃用地址，没有用于服务绑定。

开发机通过原生 IPv6 成功连接服务器 SSH 99 端口，并在 8766 端口获得 `gpu-pocket-ipv6-ok`。用户换用另一浏览器后，手机在校园 Wi-Fi 下也能看到该测试页。两个已确认的客户端都在校园网内，因此这些结果只证明校内可达，不能推断蜂窝或其他校外网络可达。

8766 临时测试服务已停止。标准 80 端口上当前保留一个诊断和 ACME 验证入口：

```text
http://[2001:da8:8002:6bd1:5d5d:9bea:1702:6bee]/ipv6-check
```

该地址仅返回测试文字，不转发 API，不使用令牌。需要使用刚才能打开页面的浏览器，关闭 Wi-Fi 和 VPN，通过蜂窝网络再测一次。测试 HTTP 地址不应填入 App；原生客户端仍要求远端 HTTPS。

## 公网证书验证尚未通过

使用官方 Certbot 5.9.0 对 Let's Encrypt 测试环境执行 IPv6 地址的 HTTP-01 验证，证书机构连接 TCP 80 超时。又使用官方 Caddy 2.11.7 对测试环境执行 TLS-ALPN-01 验证，证书机构同样无法连接 TCP 443。没有签发或启用可信生产证书。

服务器主机的 ip6tables INPUT 默认 ACCEPT，所见规则没有针对这两个入口的拒绝。服务已明确绑定上述全局 IPv6，开发机也能读取 HTTP 80 的实际 ACME webroot 文件。这些证据支持进一步排查校园网边界或外部 IPv6 路由限制，但尚不能认定所有外部网络都被阻止。

测试用 TLS 配置已撤下，Caddy 不再后台反复申请证书。当前仅保留 HTTP 80 的测试和 ACME 路由，443 没有服务监听。Quick Tunnel 与只读 API 保持运行，手机 App 地址尚未切换。

## 下一步

1. 手机关闭校园 Wi-Fi 和 VPN，在蜂窝网络访问上述 `/ipv6-check`。
2. 如果蜂窝也超时，向学校网络管理员核实该服务器前缀是否允许校外 IPv6 入站，以及如何放行 TCP 80、443。不能通过修改电脑或手机设置代替服务器侧上游放行。
3. 如果蜂窝可达但证书机构仍不可达，需要进一步定位地域或路径差异，不能把校园网内测试当作公网证书可用的证据。
4. 端口验证通过后，再申请生产 IPv6 IP 证书、启用 HTTPS、设置自动续期，最后验证未带令牌 401、有效令牌 200、控制接口 403。
5. 通过后，App 的服务地址可改成 `https://[2001:da8:8002:6bd1:5d5d:9bea:1702:6bee]`；此前继续使用已有 Quick Tunnel 地址。

Let's Encrypt 已支持免费的 IPv4 / IPv6 地址证书，不强制购买域名；IP 证书属于短有效期类型，需要自动续期。参考 [官方 IP 证书说明](https://letsencrypt.org/2026/03/11/shorter-certs-certbot)。这是证书能力说明，不代表当前服务器已满足签发条件。
